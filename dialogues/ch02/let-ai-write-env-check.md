# 让 AI 写一个环境检查脚本

## 背景

第 2 章搭好开发环境后,想用一个脚本一键确认所有依赖都装好了。这次让 AI
(Kimi)从零写出 `check_env.py`,实践本书"先把需求讲清楚,再让 AI 动手"的
基本模式。环境为 macOS + Python 3.12 + uv。

> 本对话使用的 AI:Kimi。提示词为本书 Prompt 模板 CH02-001。

## 完整对话

> 👤 你是一位 Python 工程师。我是 GIS 专业的学生,正在搭建 GIS 开发环境,
> 用 macOS,Python 3.12,用 uv 管理环境(不是 conda),搭建在本文件夹下的
> 虚拟 python 环境。
>
> 请帮我写一个 check_env.py 脚本,用来一键检查我的 GIS 开发环境是否装好,要求:
>
> 1. 检查 Python 版本(至少 3.12)
> 2. 检查能否 import:geopandas、shapely、folium、matplotlib、jupyter
> 3. 检查命令行工具是否安装:git、node、pnpm(并打印各自版本)
> 4. 最后汇总:每项用 ✓/✗ 标记,全部通过给出成功提示,否则提示有几项没过
>
> 请给出完整可运行的脚本,关键地方加中文注释解释为什么这么写。

> 🤖 脚本已创建并通过测试,运行逻辑正常。当前环境是系统默认 Python 3.9,
> 所以大部分项显示 ✗(这恰好验证了脚本的诊断能力)。
>
> 以下是脚本的核心设计说明:
>
> | 设计点 | 实现方式 | 为什么这样写 |
> |---|---|---|
> | 版本检查 | `sys.version_info` | 比解析 `sys.version` 字符串更可靠,避免小数点比较陷阱 |
> | 包检查 | `importlib.import_module()` | 比 `__import__` 更规范,支持多级包名 |
> | 命令行工具 | `shutil.which()` | 跨平台,比调用 `which` 子进程更快 |
> | 版本获取容错 | 先 `--version` 再 `-v` | 不同工具参数不同;用 `stderr=subprocess.STDOUT` 捕获 pnpm 等往 stderr 输出版本的工具 |
> | 退出码 | `sys.exit(0/1)` | 方便后续写自动化脚本或 CI 集成判断 |
>
> 脚本路径:`<项目目录>/check_env.py`
>
> 在 uv 虚拟环境中运行示例:
>
> ```bash
> uv venv .venv
> source .venv/bin/activate
> uv pip install geopandas shapely folium matplotlib jupyter
> python check_env.py
> ```
>
> 全部通过后的输出:
>
> ```
> 🎉 恭喜!所有检查项全部通过!
> 你的 GIS 开发环境已就绪,可以开始工作了。
> ```
>
> 如果需要扩展检查项(比如加 uv、pyproj、rasterio),直接修改脚本中
> `packages` 或 `cli_tools` 列表即可,无需改动核心逻辑。

## 关键时刻

- 🟢 第 1 轮:提示词把"系统(macOS)、Python 版本、包管理器(uv 不是 conda)、
  要检查的具体项、输出形式"都讲清楚了,AI 一次就给出可直接运行的脚本——
  这正是"需求讲清楚,AI 少返工"的体现。
- 🟢 第 1 轮:AI 主动给出每个设计点的"为什么"(为何用 `shutil.which`、为何
  用 `importlib.import_module`),而不只是丢代码——把工具用法变成了可迁移的知识。
- 🟡 第 1 轮:AI 把脚本建在了项目约定目录之外(一个独立测试文件夹),没有先
  确认"放哪儿"。真实项目里,应在提示词里指明目标路径,或在它动手前问一句。
- 🟡 第 1 轮:AI 的实现与本书正文版本有小差异(它用 `importlib.import_module`
  + `--version`/`-v` 兜底;正文用 `__import__`)。两种都对,但"AI 给的不等于
  教材里的"值得留意——应理解其取舍,而非照单全收。

## 复盘

这次对话验证了一个朴素但重要的经验:**把约束写进提示词,AI 的产出质量会明显
提升**。这条提示词点明了系统、Python 版本、包管理器和输出形式四个约束,所以
AI 没有反复追问、一次就给出能用的脚本,还附带了设计理由。

它"一次成功",但顺利不代表可以照单全收。两个值得复盘的点:一是 AI 自作主张
选了文件路径,提醒我们工程里"代码放哪儿"也该在需求里交代;二是它的实现和教材
版本有差异——这恰恰说明同一个需求有多种合理写法,关键是看懂每种写法的取舍,
而不是把 AI 的输出当唯一答案。下次可以追问它"为什么不放在我的项目目录",把
这类隐含决策显式化。
