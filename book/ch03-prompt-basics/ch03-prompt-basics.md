# 第 3 章 Prompt 设计基础——如何向 AI 描述一个 GIS 需求

> **本章学习目标**
> - 理解为什么 GIS 需求比一般编程需求更容易被 AI 误解
> - 掌握 Prompt 设计的五要素:角色、任务、约束、数据、输出
> - 学会用少样本提示(few-shot)、自检提示、迭代对话三种进阶技巧
> - 能判断一个长对话什么时候该重开、什么时候该继续
> - 积累一份属于你自己的 Prompt 模板库
>
> **本章的关键承诺**:读完这一章,你遇到任何 GIS 任务,都能在 2 分钟内写出一个合格的 Prompt。

## 3.1 一个让人沮丧的实验

我想先让你做一个小实验,不用打开电脑,只需要想象。

假设你是一个 AI,没有屏幕、没有手、不能问回头、不能看文件。你收到一个陌生人发来的消息:

> 帮我做个地图

你会怎么回应?

你大概率会写一段 HTML + Leaflet,给一个默认底图,放几个示例标记,然后加一段"如果你有更具体的需求请告诉我"。

这个回应没错,但它几乎对任何真实需求都不适用。用户可能想要的是:在 Web 页面展示全国 1000 个门店位置的交互式地图;或者,Python 里生成一张静态图用于论文配图;又或者,给一个非技术的老板做一张可点击的省份热力图附在 PPT 里;还可能是,三维地球上显示一个航线动画。

**同一句话,背后有完全不同的世界**。

而你是一个真实的 GIS 学生时,你在 AI 对话框里打出"帮我做个地图"的时候,这种信息损失是你几乎意识不到的——因为**你脑海里默认了太多 AI 根本没有的上下文**。

本章要教你的就一件事:**把你脑海里的上下文,一次性地、完整地搬到 AI 面前**。

---

## 3.2 为什么 GIS 需求特别容易被 AI 误解

泛泛地写 Prompt 教程,网上有几百篇。但 GIS 领域有它**特有的歧义来源**,值得专门讨论。理解这些歧义在哪里,比记几条"写好 Prompt 的七个技巧"有用得多。

### 歧义来源一:坐标系与投影

这是 GIS 领域最臭名昭著的歧义。

当你说"我有一份北京的 POI 数据",AI 不知道这份数据:

- 是 WGS84 地理坐标(全球通用的经纬度)
- 还是 GCJ-02(中国国家测绘局规定的加密坐标,高德、腾讯在用)
- 还是 BD-09(百度自己的再加密坐标)
- 还是投影坐标,如 CGCS2000 / UTM 50N / Web Mercator

这些坐标系之间的差异,最少是几十米,最多可以到几百米。AI 如果按默认的 WGS84 处理你的 GCJ-02 数据,地图上的点会**整体偏移几百米**,但代码一行不报错。

> ⚠️ **典型踩坑**:你用高德地图的 JS API 加载自己的 POI 数据(WGS84),发现所有店铺都"飘"到街对面去了。AI 给你的代码没错,但它不知道你的数据和底图坐标系不一致。

**怎么避免**:Prompt 里**明确写出数据的坐标系**。如果不知道,坦白告诉 AI "我不确定坐标系,请帮我先检查"。

### 歧义来源二:数据格式

"shapefile"和"GeoJSON"听起来像同一类东西,但在代码层面差异巨大。

- shapefile 实际上是**一组文件**(.shp / .shx / .dbf / .prj...),不是单个文件
- GeoJSON 是纯文本,可以嵌在 JS 代码里直接用
- GeoPackage 是 SQLite 数据库
- KML 是 XML
- Shapefile 有 2GB 单文件上限,字段名不能超过 10 字符,不支持中文字段名

AI 看到"我有一份数据",如果你不说格式,它会按最通用的假设来写代码——通常是 GeoJSON。结果你手里是 shapefile,它写的代码跑不动。

**怎么避免**:Prompt 里写清楚**格式、路径、大概体量**。"我有一份 shapefile,`./data/poi.shp`,约 50MB,5 万条要素"比"我有一份 POI 数据"强一百倍。

### 歧义来源三:空间关系的表述

中文里"附近"、"相交"、"包含"这些词在口语里含糊,在空间分析里都是**精确的几何操作**。

- "所有在 500 米范围内的 POI" → `ST_DWithin`
- "所有与行政区相交的河流" → `ST_Intersects`
- "所有完全被某个区域包含的点" → `ST_Contains`
- "所有与某条线接触的多边形" → `ST_Touches`

如果你只说"给我找出附近的 POI",AI 得猜:是缓冲区内的,还是最近的 N 个,还是同一街区的?它的猜测不一定错,但多半要改几轮。

**怎么避免**:把口语化的空间关系翻译成**精确描述**。"500 米范围内"、"完全包含"、"至少部分相交"都是好的说法。

### 歧义来源四:"可视化"的含义

"帮我可视化一下这些数据"是学生最常发的一句话,也是 AI 最容易跑偏的一句话。

- 可视化是指**静态图**(matplotlib 出 PNG)还是**交互式网页**(Leaflet、Mapbox)?
- 是**浏览式**(看看数据长啥样)还是**汇报式**(要发给别人看)?
- 需要加**标题、图例、比例尺**吗?
- 颜色映射要不要考虑**色盲友好**?

没说清楚时,AI 通常默认做一张 matplotlib 灰白底图,这对你写论文有用,对你做项目演示就完全不够。

**怎么避免**:写清楚**用途**。"用 Folium 做一张交互式网页地图,给项目汇报看"和"用 matplotlib 画一张论文插图,灰度打印也能看清"会得到完全不同的代码。

### 小结

GIS 需求里的歧义,**大部分不是 AI 的问题,而是你还没意识到自己没说清楚**。记住这四类歧义来源,你的 Prompt 质量会立刻提升一个档次。

下一节我们把这些零散的经验,归纳成一套可复用的结构。

## 3.3 Prompt 五要素:角色、任务、约束、数据、输出

本书推荐你用下面这五要素的结构写任何 GIS 相关的 Prompt。这不是唯一的方法,但它**对 GIS 场景特别有效**,而且足够简单、容易记住。

### 要素一:角色(Role)

**告诉 AI 你希望它扮演什么角色**。

比较:

> 👤(A)帮我写个地图

> 👤(B)你是一个熟悉 Leaflet 的前端工程师,有 GIS 背景。帮我写个地图

(B)会得到更 GIS 化的代码——它会考虑坐标系、会选合适的底图、会加空间相关的交互。(A)得到的可能是一段只会加标记的通用代码。

**常见 GIS 角色**:

- `你是一个熟悉 GeoPandas 的 Python 开发者`
- `你是一个 PostGIS 专家`
- `你是一个有 10 年经验的 WebGIS 工程师`
- `你是一个注重代码可读性的教师,正在给初学者写示例`
- `你是一个严谨的地理数据分析师,注重结果可验证`

角色一句话就能写完,但**效果经常比你以为的更显著**。它不是魔法,但它给了 AI 一个"回答的风格基准"。

> 💡 **提示**:最后一个角色"注重结果可验证的数据分析师"特别有用。它会让 AI 在产出代码里主动加入数据检查、边界情况处理、print 关键中间值,对初学者帮助极大。

### 要素二:任务(Task)

**用一句话说清楚你想要什么结果**。

比较:

> 👤(A)帮我处理一下数据

> 👤(B)把全国地级市 GeoJSON 和城市人口 CSV 合并成一个新的 GeoJSON,每个地市要素的 properties 里要有人口字段

(A)AI 得脑补三步,每一步都可能猜错。(B)AI 可以直接动手,因为结果形态已经定义好了。

**写任务描述的三个建议**:

一是**用动词开头**:生成、计算、合并、过滤、可视化。避免"关于……"、"有个问题……"这种模糊的开头。

二是**指向最终产物**:你最终想要的是 HTML 文件?PNG 图?一张 DataFrame?还是一段 SQL?明确下来。

三是**一次只做一件事**:如果任务里有多个环节,要么拆成几次对话,要么在任务里**分步骤列清楚**(这在下文"输出要素"里还会讲)。

### 要素三:约束(Constraints)

**告诉 AI 什么能做、什么不能做**。

这是很多人忽略但其实最关键的要素。约束越明确,AI 产出越接近你真正想要的。

**GIS 场景下的常见约束**:

```
- 用 GeoPandas 不要用 arcpy
- 不要引入新的依赖,只用 Python 标准库 + 我已经装了的 geopandas
- 代码要能在 Python 3.12 下运行
- 数据量很大(100 万行),请用流式处理不要一次性读入内存
- 输出必须是 WGS84 坐标系
- 中文字段名需要保留不要改
- 不要用 matplotlib,用 Folium
- 考虑 Windows 的路径分隔符问题
```

**特别值得强调的约束**:

**性能约束**:如果你的数据量大,不说 AI 不知道。"处理 100 万条点数据"和"处理 100 条点数据"的代码策略差异巨大。

**版本约束**:某些库的 API 不同版本差异大(如 GeoPandas 0.x vs 1.x)。如果你遇到过版本相关的报错,写进 Prompt。

**风格约束**:"代码要有中文注释"、"变量名用英文,注释用中文"、"加类型注解"。这些看似表面的约束,长期累积能让你的代码风格统一。

### 要素四:数据(Data)

**AI 要知道它在和什么样的数据打交道**。

不给数据描述的 Prompt 就像"盲人摸象"——AI 的代码是基于猜测的。

**数据描述应该包括**:

- **位置**:路径或 URL
- **格式**:shapefile / GeoJSON / CSV / PostGIS 表 / ...
- **规模**:大小、行数、要素数
- **结构**:有哪些字段,哪些是几何字段,哪些是属性字段
- **坐标系**:EPSG 代码或坐标系名称
- **样例**:给 2–3 行真实数据最有用

**最好用的技巧:贴一段真实数据**。

比较:

> 👤(A)我有一个城市 POI 的 CSV

> 👤(B)我有一个 CSV,前三行长这样:
> ```
> name,category,lon,lat,city
> 华联超市,超市,116.4074,39.9042,Beijing
> 麦当劳(建国路店),餐饮,116.4523,39.9099,Beijing
> 101 中学,教育,116.3821,39.9562,Beijing
> ```

(B)让 AI 省去一切猜测,它知道字段名大小写、知道坐标是经度在前还是纬度在前、知道是不是有中文、知道分类值长啥样。**贴三行真实数据是 Prompt 工程最有投入产出比的技巧之一**。

如果数据有敏感信息,可以手工造几行**结构相同但内容虚构**的样例贴上去。

### 要素五:输出(Output)

**告诉 AI 你希望它怎么组织回复**。

默认情况下,AI 会给你写一段解释 + 一段代码 + 一段使用说明。这对初学者有用,但当你进入熟练阶段,会希望更精简、或者更结构化。

**常见的输出约束**:

```
- 只输出代码,不要任何解释
- 代码放在一个完整文件里,不要拆成片段
- 先给步骤拆解,每步一句话,再给完整代码
- 用 Python 的 notebook 格式(# %% 分隔 cell)
- 如果有风险点,在代码中用 TODO 注释标出
- 遇到你不确定的地方,列出来不要猜测
```

最后一条特别有用。GIS 场景下,AI 经常因为缺信息而"硬编"参数(比如瞎写一个 EPSG 代码),加这一条约束能显著降低这种风险。

### 五要素的完整示例

把上面的要素组合起来,一个合格的 GIS Prompt 大概长这样:

> 👤 **[角色]** 你是一个熟悉 GeoPandas 的 Python 开发者,注重代码可读性与可验证性。
>
> **[任务]** 请帮我计算每个地级市离最近的三甲医院的直线距离,并把结果写回地级市 GeoJSON 的 properties 里。
>
> **[约束]**
> - 用 GeoPandas,不要用 arcpy
> - Python 3.12
> - 输出坐标系保持 WGS84,但距离计算要先投影到 EPSG:3857 再算(这样单位是米)
> - 如果某个地级市没有三甲医院数据,填 None 不要报错
> - 代码要有中文注释
>
> **[数据]**
> - 地级市边界:`./data/cities.geojson`,约 300 个要素,字段:`city_name, province`
> - 三甲医院:`./data/hospitals.csv`,前 3 行:
>   ```
>   name,city,lon,lat
>   北京协和医院,Beijing,116.4169,39.9133
>   上海华山医院,Shanghai,121.4352,31.2230
>   广州中山一院,Guangzhou,113.2808,23.1281
>   ```
>
> **[输出]**
> - 一个完整的 Python 脚本,保存为 `compute_distance.py`
> - 脚本开头用注释说明三步:读数据 → 计算距离 → 写回
> - 遇到不确定的地方用 `# TODO:` 注释标出

这个 Prompt 看起来长,但实际写下来不超过两分钟,却能省掉之后 5–10 轮的来回澄清。

## 3.4 少样本提示:一个例子胜过十句话

上一节的五要素是"结构化描述"。本节讲的少样本提示(few-shot prompting)是另一种策略——**不解释,直接给例子**。

### 什么时候用少样本提示

当你的任务符合以下任一特征,少样本比解释更有效:

- **输入输出格式很具体**,但用语言描述起来绕
- **风格、口味很关键**,比如你希望代码保持某种风格
- **规则有例外**,你很难用文字穷举

### 例子一:数据清洗

假设你要把一份脏兮兮的地址数据规范化。用解释的话,你得写"去掉多余空格、统一为 X 省 Y 市 Z 区、补全省份……"。用例子很多:

> 👤 请帮我写一个函数,把下面的地址字符串规范化。几个例子:
>
> ```
> "北京朝阳区建国路  88号"  → "北京市朝阳区建国路88号"
> "上海 浦东 陆家嘴环路"    → "上海市浦东新区陆家嘴环路"
> "广州番禺 大学城"         → "广东省广州市番禺区大学城"
> "XX 省 深圳 南山"         → "广东省深圳市南山区"
> ```
>
> 请总结规则,然后写出函数。

AI 会先复述它从例子里总结的规则,再写代码。比你写十行约束更准。

### 例子二:SQL 风格

你希望 AI 写出来的 PostGIS SQL 符合某种格式:

> 👤 请按下面的风格写 PostGIS 查询:
>
> ```sql
> -- 示例:查找北京所有 500 米内有地铁站的餐厅
> SELECT r.name, r.geom
> FROM restaurants r
> WHERE EXISTS (
>   SELECT 1
>   FROM subway_stations s
>   WHERE ST_DWithin(r.geom::geography, s.geom::geography, 500)
> )
> AND r.city = 'Beijing';
> ```
>
> 风格要点:用 EXISTS 不用 JOIN、用 geography 类型计算距离、每个子句换行、表别名简短。
>
> 现在请按这个风格写:查找上海所有 300 米内有公交站的学校。

AI 写出来的会和你给的例子高度一致。

### 例子三:错误修复

你甚至可以用"错误示例"来引导 AI 避免某种写法:

> 👤 我要写一个函数检查两个 GeoJSON 是否覆盖同一区域。**不要**这样写:
>
> ```python
> # 反面示例:粗糙
> def same_area(g1, g2):
>     return g1.bounds == g2.bounds
> ```
>
> 请写一个更严谨的版本,考虑精度容差、坐标系一致性、空几何情况。

这种"反例 + 要求"的写法,比正面描述"写得严谨一点"有效得多。

### 少样本提示的经验法则

**例子数量**:2–4 个最好。1 个可能让 AI 泛化不足,5 个以上容易让对话太长。

**例子要有多样性**:不要三个都是简单情形。每个例子覆盖不同边界条件。

**最后一个例子可以包含"陷阱"**:比如一个容易被漏掉的特殊情况,强迫 AI 注意到它。

## 3.5 迭代式对话:多轮逼近需求

Prompt 不一定要一次写完美。**更常见的模式是通过多轮对话逐步逼近**。

这一节讲如何把"一轮对话"升级为"一次有效的对话会话"。

### 模式一:渐进式细化

第一轮给一个粗略描述,看 AI 怎么理解,然后基于它的回复修正。

> 👤 **轮 1**:帮我做一个地图展示北京地铁线路
>
> 🤖 (AI 写了一个 Leaflet 的基础版本,有站点但没线路)
>
> 👤 **轮 2**:站点是有了,但我要的是整条线路(一条曲线)的展示,不是站点。每条线一种颜色。
>
> 🤖 (AI 改了,但颜色是默认的)
>
> 👤 **轮 3**:颜色要用北京地铁官方色(1 号线红、2 号线蓝……)。此外,鼠标悬停线路时要变粗并显示线路名。

每一轮的 Prompt 都比上一轮**更短**——因为前面的上下文 AI 已经记住了。这是迭代对话的核心优势:**你不需要每次都重复所有信息**。

### 模式二:先讨论方案,再写代码

当任务复杂时,**不要急着让 AI 写代码**。先和它讨论方案。

> 👤 **轮 1**:我想做这件事:给定一份全国县级行政区划 GeoJSON 和一份 POI 点集,计算每个县 POI 密度并可视化。**先不要写代码**,请列出你的步骤、技术选型、可能的陷阱。
>
> 🤖 (AI 列出 5 步方案)
>
> 👤 **轮 2**:第 3 步你说用 `gpd.sjoin`,但我数据量大(100 万 POI),会不会很慢?有没有更快的方案?
>
> 🤖 (AI 建议用 R-tree 索引或 PostGIS)
>
> 👤 **轮 3**:好,我们用 PostGIS 方案。现在请按这 5 步写代码。

这个模式的价值在于:**AI 变成了你的"结对程序员",而不是"代码生成器"**。你们一起设计,再一起实现,出问题的概率会低很多。

### 模式三:给反馈而不是给指令

当 AI 给的代码不对时,比起"改一下第 3 行",更有效的是说出**你发现的问题**。

比较:

> 👤(A)第 3 行改成 `.to_crs(3857)`

> 👤(B)运行的时候,每个县算出来的 POI 密度都差不多,不太合理。我怀疑是不是你用了地理坐标系来算面积?

(A)让 AI 变成了打字员。(B)让 AI 自己找问题、学到教训、甚至可能发现更深层的 bug。

尤其是当你**不确定问题在哪里**时,把现象描述清楚,让 AI 去诊断,往往比你自己猜快。

### 多轮对话的三个常见陷阱

**陷阱一:错误累积**。AI 在第 3 轮理解错了,你没纠正,继续往下聊,第 10 轮时已经南辕北辙。**办法**:每隔几轮让 AI 总结一下"当前我们在做什么",早发现偏差。

**陷阱二:上下文膨胀**。对话越长,AI 能"记住"的越少。到某一时刻,它会开始忘掉早期细节。**办法**:见下一节。

**陷阱三:先入为主**。AI 在第 1 轮给了一个方案,后续几轮都在那个方案的框架里修修补补。有时候**整体方案就是错的**,但你不容易察觉。**办法**:偶尔重开一次对话,重新描述需求,看 AI 新一轮给的方案和之前差异多大。

## 3.6 让 AI 自检:避免跑偏的黄金技巧

这是本章最值得记住的一个单独技巧。它很简单,但能显著降低 AI 跑偏的风险。

### 技巧:请 AI 先复述需求

在你给完完整 Prompt 之后,加一句:

> 在开始写代码之前,请用你自己的话复述一下我的需求。如果有任何不确定或歧义,请列出来。

这一句话能换来两件好东西:

**第一**,AI 会把它的理解展示出来,你能**立刻发现误解**。如果它理解错了,你在这一刻修正,比后面重写代码代价低得多。

**第二**,AI 会**主动列出歧义**——"您没提到坐标系,我假设是 WGS84 可以吗?"、"您说的三甲医院名单是否是全国范围?"。这些问题,不问你可能想不到,AI 问了你才意识到"对啊,我得说清楚"。

### 一个真实的例子

一位学生给 AI 的 Prompt 是:"找出北京所有大学的邻接地铁站"。

加了"请先复述"之后,AI 回复:

> 我理解您的需求是:给定一份北京大学(即高等院校,不是北京大学这所学校)的位置数据,以及北京地铁站的位置数据,找出每所大学附近的地铁站。
>
> 有几点我不确定:
>
> 1. "邻接"的具体标准是什么?最近的一个?步行 500 米内的所有?还是同一街区?
> 2. 您手头有数据吗?如果没有,我需要现爬?
> 3. "北京所有大学"——是指所有高等院校,还是只包括本科院校?
> 4. 输出格式希望是表格、GeoJSON、还是可视化地图?

这四个问题,学生原本可能到第 5 轮对话才会一个个意识到。现在 AI 一次全问清了,学生只用花 2 分钟回答,就可以开始干活。

### 什么时候必须加这一句

以下场景我建议每次都加:

- **任务涉及多个数据源**(容易搞错哪个和哪个配对)
- **任务有多个歧义词**(如"附近"、"相关"、"类似")
- **输出形态不明显**(用户没说清楚要什么格式)
- **你自己都没完全想清楚需求**时(让 AI 帮你梳理)

短平快的任务(如"写一段读取 shapefile 的代码")不需要加,浪费时间。

## 3.7 上下文管理:长对话什么时候重开

随着对话变长,AI 的表现会变差。这不是玄学,是模型的客观限制。

### 长对话为什么会变糟

每一轮对话,AI 都要把**之前所有轮次**重新读一遍,才能给出下一轮的回复。对话越长,上下文窗口越满,AI 就越难:

- 记住早期的细节
- 保持需求的一致性
- 给出高质量的新回复

到某个阈值后,你会观察到:AI 开始重复自己、开始"忘记"之前的约束、开始给出和早期相矛盾的建议。

### 识别"对话疲劳"的信号

以下信号出现两个以上,就该考虑重开了:

- AI 写的代码和你五轮前讨论好的风格不一致
- AI "忘记"了你早期给过的字段名或约束
- AI 给出的新代码在修补已经不合理的旧方案
- AI 的回复明显变慢或变短
- 你自己看着对话历史,发现要滚动很久

### 如何优雅地"重开"

硬重开(新开一个对话)并不意味着一切从头来。推荐的流程:

**第一步**,在快要放弃的对话里,让 AI 帮你总结一下当前状态:

> 👤 我们聊了很久了。请帮我总结一下:我们最终确定的需求是什么?当前代码解决了什么,还有什么待解决?

AI 会产出一段结构化的总结。

**第二步**,把这段总结作为新对话的第一条消息的一部分:

> 👤 **[角色]** 你是一个 GIS Python 工程师。
>
> **[上下文]** 我之前和 AI 讨论过这个需求,当前状态是:[粘贴上面的总结]
>
> **[任务]** 现在我需要继续解决:[剩下的问题]

这样新对话继承了全部关键信息,但没有背上所有废话的包袱。

### 一个经验数据

根据本书作者的实战经验,**在 Claude 和 GPT 这一代模型上,一个 GIS 相关对话超过 15 轮就值得考虑重开**。超过 25 轮几乎必须重开——再聊下去你会越改越乱。

这个经验数据会随模型升级变化,但"对话有寿命"这个基本事实不会变。

## 3.8 关于"Prompt 技巧"的清醒认知

讲到这里,我要做一个逆转。

本章教了你五要素、少样本、迭代、自检、上下文管理。这些都是真实有效的技巧。但**不要把它们变成宗教**。

我想说三件"反过来"的话。

**第一**,**最好的 Prompt 是短的**。五要素不是让你写一封"情书"给 AI。熟练之后,你的 Prompt 会越来越短,因为你学会了挑最关键的信息先给。本章前面的 Prompt 模板看起来长,是为了演示结构,实战中大多数对话会在五行之内完成。

**第二**,**Prompt 技巧救不了错误的需求**。如果你对要做的事情本身没想清楚,你的 Prompt 再工整也没用。很多时候,"写好 Prompt"的瓶颈在"想清楚需求",不在"遣词造句"。

**第三**,**AI 的能力在进化,部分技巧会过时**。比如早期的 Prompt 工程需要大量的"Let's think step by step"类技巧,现在的模型内置了推理能力,这种技巧已经多余。本书教的五要素之所以持久,是因为它本质是**人类沟通的基本结构**(背景-任务-约束-条件-目标),不是 AI 的怪癖。

所以:**学 Prompt 技巧的终极目标,是让你不再需要刻意练 Prompt**。就像学外语最终是为了不再需要翻字典。

## 3.9 本章 Prompt 模板库

本节汇总本章推荐的几个常用 Prompt 模板。你可以把它们保存到自己的 `prompts/` 文件夹里,长期积累自己的模板库。

### 模板 A:通用 GIS 任务五要素模板

```
[角色] 你是一个熟悉 ___ 的 ___ 开发者。
[任务] 请帮我 ___ ,最终产物是 ___ 。
[约束]
- 技术栈:___
- 性能要求:___
- 不要:___
[数据]
- 位置:___
- 格式:___
- 规模:___
- 样例:
  ```
  ___
  ```
[输出]
- 形态:___
- 风格:___
- 未知项:请列出来不要猜测
```

### 模板 B:任务规划讨论(不写代码先讨论)

```
我想做这件事:___ 。

**不要写代码**,请:
1. 列出完成这件事的主要步骤(不超过 7 步)
2. 每一步的技术选型与理由
3. 这个任务最可能踩的 3 个坑
4. 你对我的数据/需求的任何疑问
```

### 模板 C:让 AI 自检需求

```
[完整 Prompt 内容]

在开始写代码之前,请:
1. 用你自己的话复述一下我的需求
2. 列出你认为可能有歧义或不确定的点
3. 如果有重要的信息我没提供,直接问我

等我确认你理解正确了,再动手写。
```

### 模板 D:代码审查(AI 写完代码后追问)

```
请审查你刚才写的代码,回答:
1. 哪些地方你不太确定,可能有 bug?
2. 有没有边界情况没处理?
3. 性能上有没有明显的问题?
4. 如果要把这段代码投入生产,还缺什么?
```

### 模板 E:错误诊断

```
运行时遇到这个错误:
```
[完整错误堆栈]
```

我的环境:
- 操作系统:___
- Python 版本:___
- 相关包版本:___

请:
1. 解释错误的含义
2. 最可能的原因是什么
3. 给出修复建议(按可能性排序)
```

### 模板 F:长对话重开

```
我之前和 AI 讨论过一个需求,中间比较混乱。重新整理如下:

**背景与目标**:___
**已完成的部分**:___
**当前卡住的地方**:___
**代码当前状态**:
```
[代码]
```

请接下来帮我解决卡住的部分。
```

### 模板 G:模板的模板(教你怎么写自己的模板)

其实最重要的不是用别人的模板,是**发现自己的高频场景,为它们定制模板**。

当你发现某一类任务你一周要重复三次以上,就该为它写一个模板。比如:

- 每次做栅格分析,都要重复说一遍"考虑 NoData、分块处理、坐标系对齐" → 写一个栅格分析模板
- 每次让 AI 写 PostGIS 查询,都要强调格式风格 → 写一个 SQL 风格模板
- 每次接手学弟学妹的烂代码,都要 AI 先审查再改 → 写一个代码审查模板

**这是本章留给你最长期的作业**。

本章做了这些事:

Prompt 工程不是一门玄学,它是一门**把脑子里的东西准确搬到屏幕上的功夫**。这门功夫你每天都在用,只是过去是对人,现在多了一个对 AI。两者底层规律惊人地一致。
